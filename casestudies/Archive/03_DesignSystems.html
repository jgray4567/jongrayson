Enterprise Design Systems

How to build a design system that 200+ engineers actually use, scales across 4+ platforms, and makes iteration faster while maintaining consistency. The unglamorous work that enables everything else.

THE PROBLEM

Every Designer Rebuilding Buttons

Multiple mission-critical platforms were built by different teams, at different times, with different tools. The result: visual inconsistency, duplicated component work, and nightmare maintenance.

When a usability issue was discovered in button behavior, it had to be fixed in 4 separate codebases. When branding changed, teams had to re-implement across platforms independently. Designers spent 40% of time rebuilding components instead of solving new problems.

More critically: inconsistency created cognitive friction for users switching between systems. One platform's "Save" pattern worked differently than another's. Users had to relearn behaviors with each app.

A design system isn't about pixels. It's about scaling trust, consistency, and team velocity. — Brad Frost, Atomic Design
STRATEGY

Building Adoption, Not Just Documentation

Phase 1: Audit & Synthesis

Before designing anything, we catalogued what already existed:

  • Visual components across 4 platforms (buttons, forms, modals, etc.)
  • Interaction patterns (how users completed common tasks)
  • Conflicts (where platforms diverged in similar use cases)
  • Technical constraints (legacy systems vs. modern stacks)

The audit showed ~60% pattern overlap—components that should be identical but weren't. These became the system's foundation.

Phase 2: Design Foundation

Rather than creating idealized components, we extracted from production systems. The best existing button from any platform became the canonical button. The best form pattern became the standard. This meant teams recognized themselves in the system—it wasn't foreign.

We documented not just the component, but the thinking behind it:

  • When to use this vs. alternative patterns
  • Mobile adaptations (critical for systems with mobile users)
  • Accessibility requirements built in
  • Common mistakes and how to avoid them

Component Recipes, Not Prescriptions

Documentation wasn't "Use this button." It was "Here's why we chose this interaction. Here's how to adapt it for your context. Here's how mobile changes it." This gave teams autonomy while maintaining alignment.

Phase 3: The Governance Model

Most design systems fail because governance is either too loose or too strict. Ours used a tiered approach:

  • Core Components (Protected): Buttons, forms, alerts. Any change required cross-team review.
  • Patterns (Guided): Workflows, layouts. Teams could adapt within guidelines.
  • Experimental (Monitored): New components. If proven useful across teams, promoted to Core.

This balanced consistency with innovation. Teams didn't feel constrained; they felt supported.

EXECUTION & ADOPTION

Making Systems Irresistible to Use

The Components Library (Figma)

We built a living Figma library with:

  • Main components + variants (color, size, state)
  • Annotations for spacing, color tokens, behavior
  • Interactive prototypes showing mobile responsive behavior
  • Accessibility notes linked to WCAG standards

Mobile was prioritized: every component showed mobile, tablet, and desktop variants. Designers could instantly see how a button adapted across screen sizes.

Code Implementation

Engineers got Storybook components they could import directly:

  • React components with prop documentation
  • CSS variables for theming
  • Built-in accessibility (ARIA labels, keyboard navigation)
  • Mobile-first responsive breakpoints

The barrier to adoption was deliberately lowered: `npm install @platform/design-system` and you could start using components immediately. No research, no decisions, no inconsistency.

Mobile-First Implementation: All components were designed and coded mobile-first. Desktop was considered an enhancement. This meant mobile users got fast, optimized components, and desktop users got components that worked well at any size.

Adoption Strategy

The key to adoption: show value immediately.

  • Ran workshops for each team (1 hour, hands-on)
  • Identified "quick wins"—easy migrations that saved time
  • Showcased before/after metrics (design velocity, consistency improvements)
  • Created a Slack channel for questions and feedback
  • Monthly "system health" reports showing adoption rates, component usage, emerging patterns

After 6 months, adoption reached 78% of new components. Within 18 months, 92%.

Qualitative Impacts

  • New team members could contribute meaningful design work in their first week (vs. first month)
  • Usability issues found in one platform were automatically fixed across all platforms
  • Mobile users experienced consistency; switching apps didn't require relearning patterns
  • Teams could experiment with new patterns in the "Experimental" tier without risk

Most tellingly: designer morale improved. Designers stopped rebuilding buttons and started solving real problems. The system didn't constrain creativity; it freed it.

LESSONS FOR TEAMS & SCALE

Systems Are Cultural, Not Just Technical

Insight 1: Governance Is Negotiation

Tight governance feels safe but kills adoption. Loose governance feels fast but creates chaos. The answer: tiered governance that changes based on maturity.

Insight 2: Adoption Requires Empathy

We didn't mandate the system. We demonstrated value. We made migration easy. We listened to concerns. Adoption happened because it was easier than not adopting.

Insight 3: Mobile-First Thinking Scales Beyond Mobile

Designing for mobile forced hard choices about components. Which buttons matter? Which can be simplified? Those choices made desktop better too.

"A design system is not a product. It's a service your design organization provides to itself." Framework from conversations with 15+ teams building systems

Insight 4: Consistency Is Strategic

Inconsistency isn't a design problem; it's a business problem. It slows teams, creates confusion, and burns money. A system that scales consistency is a system that scales revenue.

This is relevant to consumer AI products: consistency across onboarding, settings, help, and app features determines whether users develop intuitive mental models or stay confused. Design systems enable that consistency.
